# 组件职责与发布验收边界

本文件记录 Core、Runtime、CLI、Client2 的目标职责。修改日期：2026-11-17。
它同时列出尚未完成的拆分，不能用目标约定证明当前实现已经完成。

## 当前基线

- 本轮固定 Runtime `v2.0.0-dev.23`，沿用其锁定的已发布 Core SDK。
- CLI、Client2 独立发布，通过协议和所需能力配合，不要求版本号或提交号一致。
- 本轮不修改 Runtime/Core、协议或数据库实现，也不发布新的 Runtime/Core。
- 固定基线若缺少必要接口，先提供复现、最小修改方案和影响，由用户决定。

## 职责表

| 能力 | Core | Runtime | CLI／Client2 宿主 |
| --- | --- | --- | --- |
| 数据库格式、加密和底层记忆算法 | 提供实现及兼容约束 | 调用并管理数据库生命周期 | 发起操作及展示结果 |
| 登录、注册、同步、recall、remember | 提供底层能力 | 提供核心操作、事务及 RPC／MCP | 收集用户输入、处理交互及续接 |
| 模型执行、推理和索引 | 提供执行能力及必要参数校验 | 执行宿主提供的模型配置，管理核心任务 | 选择模型及资源路径，传入配置 |
| 模型和组件下载、安装、升级、卸载 | 不承担 | 不承担 | 负责来源验证、下载、安装及选择 |
| 私钥持久保管、系统钥匙串 | 不承担系统保管 | 不读取系统钥匙串，不自行找回私钥 | 保管、读取并安全传入 |
| 开机自启、Runtime 进程维护 | 不承担 | 提供核心服务及受控退出 | 注册自启，拉起、停止、更新和维护 Runtime |
| agent-config、宿主配置 | 不管理宿主文件 | 仅应用确实属于核心的运行参数 | 负责读取、默认值、校验、原子持久化及输出 |
| CLI 命令和插件入口 | 不承担 | 不嵌入旧宿主命令实现 | 保持命令、参数、退出码和机器可读输出契约 |
| Client2 界面和桌面偏好 | 不承担 | 不承担 | Client2 负责，必要时调用明确的宿主接口 |

Runtime 可以验证推理所需的格式、维度和执行能力，但不能用宿主下载目录、
某个默认模型名称或组件安装策略限制模型选择。宿主传入无效配置时，应明确失败。

## 配置的归属

`rsrs agent-config --json` 与 `rsrs --client-only agent-config --json` 均是
CLI 的配置读取。`--client-only` 限制副作用，不改变命令的归属。

两种读取必须返回一致的有效配置和既有输出字段。读取不要求 Runtime 已安装、
运行或解锁，不下载组件、不打开数据库、不读取钥匙串，也不创建或修改配置文件。
未配置时使用明确的默认值；存在但损坏的配置必须报告错误，不能当成空配置继续。

兼容字段 `read_heat_runtime`、`recall_fusion_runtime` 保留，但本地读取的两组回执均标记
`scope: "host_configuration"`、`runtime_verified: false`。其中 `effective` 仅表示本命令
按配置、默认值和环境变量解析的宿主设置，不证明 Core 支持该设置或常驻 Runtime 已应用。
`read_heat_runtime.loaded` 与 `pending_reload` 返回 `null`，明确表示真实加载状态和待重载状态未知；
不能从配置值推导这两个状态。`applies: "next_query"` 是配置的适用时机，不是已经生效的回执。
界面应显示本地配置，不能将这些字段展示为已经验证的核心运行态。

`agent-config --set` 的语法校验与配置持久化也属于宿主。设备模式保存为
`client.json` 的 `service_mode`；所选账号的其他代理设置保存到该账号的
`agent.json`。设置影响核心行为时，宿主通过明确的核心控制操作，或经过身份核验的
暂停、重启和恢复流程使其生效。不能仅把写宿主文件的 Runtime 方法换一个名字。

配置保存必须保留原子替换、并发修改检查、账号及安装身份核验，以及必要的维护事务。
已有操作按原操作编号查询和恢复；丢失回执时不能重放，也不能因为目标值相同就补造成功。
“已保存”和“常驻 Runtime 已应用”必须分别有证据，不能用前者代替后者。

## 密钥与进程

1. CLI 或 Client2 安装并核验 Runtime 的版本、来源、文件摘要和运行身份。
2. Runtime 可以先以锁库状态启动。没有宿主输入的重启必须保持锁库。
3. 宿主按自身策略从系统钥匙串或用户输入获得私钥，通过受验证的私有通道传入。
4. Runtime 接收所需密钥材料后执行核心解锁，不把密钥反向持久化到系统钥匙串。
5. 开机自启由 CLI 或 Client2 注册和执行。启动后由宿主检测锁库状态并传钥。

其他集成 agent 也可以作为宿主自行管理密钥。密钥不能放入进程参数、日志或普通操作回执。
未知的登录或密钥操作必须保留原事务，不能以再次认证掩盖失败。

关闭记忆功能时，宿主保留旧 CLI 的空结果及静默文本行为。与此同时，未解锁的 Runtime
仍必须拒绝业务读取。切换 normal／readonly 模式不等于提供了密钥，不能因此自动建库。

## 旧入口与升级兼容

保留既有 `rsrs` 命令名、参数、退出码，以及插件依赖的 JSON、标准输出和 MCP 契约。
内部职责调整不应要求旧插件改用 Runtime 的宿主兼容接口。

历史升级重点是数据库。旧正式版及改变数据库格式的 DEV 检查点升级后，必须验证：

- 原密钥能够解密旧记录，数据库完整性及待同步数据保留。
- 升级后继续 remember、recall 和同步，独立设备可解密同步结果。
- 中断、错误密钥和并发冲突明确失败，且不破坏源库或覆盖无关目标数据。

数据库格式未变的 DEV 不增加 DEV→DEV 组合。不要求旧 CLI 调用新 Runtime，
也不把旧会话、旧凭据位置或派生索引的保留作为历史兼容条件。

## 发布与验收

PR 阶段仅执行受影响的既有检查、构建和必要定向复验，不重复完整原生矩阵。
CLI 与 Client2 的独立阻塞并行处理；CLI 优先发布，因为插件和既有入口依赖它。

发布前完成必要定向回归及候选检查，发布已验证的同一批字节。完整多平台原生验收仅在
最终候选／公开 Release 阶段并行运行，并核对产物来源、版本和摘要。既有发布保护不能绕过。

最终验收必须覆盖安装升级、宿主自启和进程维护、安全传钥、重启锁库及自动解锁、
登录和钥匙续接的事务一致性与保存确认、同步、remember／recall，以及上述历史数据库升级。
只用隔离合成账号、钥匙串和数据库。源码 CI、契约测试或报告文件存在均不能代替真实产物证据。

CLI 与 Client2 的公开 DEV 可获取、职责文档和实现一致、必要产物验收全部通过后，
才可宣布本轮完成。
