# Local database snapshots

`rsrs snapshot create --note "before maintenance"` creates a consistent SQLite copy of the current library, including committed WAL data. It requires the current account key, writes private files (0600 under a 0700 directory on Unix), removes access grants from the copy and publishes a manifest only after verification. The live database and its grants are unchanged. `rsrs snapshot list` verifies each published manifest, hash, schema and SQLite integrity before listing it.

The snapshot is a local database copy. Existing local metadata/index columns can contain plaintext; this is not whole-file encryption. Protect snapshots like the original library. The manifest contains no account key or session credential and is not an authorization document. It records file integrity, account/library fingerprints, schema and pinned SDK/model metadata. An encrypted challenge in the database independently verifies the account key, including for an empty library.

`rsrs snapshot restore <full-id> --confirm` is a host CLI operation. It coordinates the owned runtime shutdown, takes the library ownership lock, validates the selected snapshot and key, and creates a durable pre-restore snapshot. A busy checkpoint or remaining SQLite sidecar refuses replacement. The implementation never deletes a live WAL/SHM file. A verified private temporary database is replaced atomically, then the runtime reopens the restored library. A startup failure invokes the normal rollback path using the retained pre-restore snapshot.

Restoring is limited to the same account, library location and initialized schema. An older/different schema requires an explicit migration path; it is not silently treated as compatible. Access grants are not revived. Physical crash, full-disk and Windows file-sharing scenarios require their respective runtime tests; a passing unit test is not evidence that all those scenarios were exercised.

Restoration does not roll back the server. Sync is quarantined in the restored database before replacement; automatic and explicit synchronization refuse before contacting the remote. Inspect the local/remote differences using read-only diagnostics. After deciding how to reconcile them, read `rsrs memory-revision --json` and explicitly run `rsrs snapshot resume-sync --reviewed-revision <token>`. If local memories changed since that revision, resumption is refused. Remote conflict writes and sync reset also respect quarantine.

A purge of live data does not erase older snapshot copies. No snapshot deletion command or automatic snapshot retention policy is introduced here. `memory_restore` in MCP still restores one tombstoned memory; it is unrelated to database snapshot restore and does not expose this host lifecycle operation.
